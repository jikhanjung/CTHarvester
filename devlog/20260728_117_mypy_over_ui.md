# mypy가 `ui/`까지 — 그리고 세 곳이 서로 다른 mypy를 돌리고 있었던 문제

2026-07-28

## 배경

mypy는 2026-07-27에 게이팅으로 전환됐지만 범위는 `core/`와 `utils/`뿐이었다.
`pyproject.toml`에는 `ui.handlers.*`에 대한 per-module strict 설정이 이미 들어
있었는데, 아무도 그 경로를 mypy에 넘기지 않아서 mypy 스스로 "unused config"로
보고하는 상태였다. 남은 일은 활성화가 아니라 **범위**였다.

C901 래칫과 같은 방식 — 디렉토리 하나씩, 깨끗해진 뒤에 추가 — 을 따랐다.

## `ui/`에서 나온 것: 6건

측정해보니 예상보다 훨씬 적었다. 4개 파일에 6건.

| 위치 | 내용 |
|---|---|
| `ui/errors.py` (3) | `ERROR_MESSAGES` 딕셔너리의 값이 서로 arity가 다른 람다라 공통 타입이 `object`로 좁혀짐 |
| `ui/exception_handler.py` | `show_error`에 `QWidget \| None`을 넘기는데 시그니처는 `QWidget` |
| `ui/handlers/export_handler.py` | `Image.open()`의 `ImageFile`에 `.crop()`의 `Image`를 다시 바인딩 |
| `ui/main_window.py` | `Qt.lightGray` — 스텁상 `Qt.GlobalColor`의 멤버 |

`errors.py`는 `dict[ErrorCode, Callable[..., ErrorMessage]]` 선언으로 해결했다.
파라미터를 열어둔 것은 의도다 — `get_error_message()`가 호출자의 인자로 부르고
`TypeError`가 나면 인자 없이 다시 부르는 구조라, 팩토리들의 arity가 제각각인
것이 설계다. 그 사정을 주석으로 남겼다.

`show_error` / `show_error_dialog`는 시그니처를 `QWidget | None`으로 넓혔다.
`_show_error_safely()`가 **의도적으로** `None`을 넘긴다 — UI가 이미 무너진
상태에서 에러를 보고하는 경로이고, `QMessageBox(None)`은 Qt에서 유효한 최상위
다이얼로그다. 호출부가 옳고 시그니처가 좁았던 쪽이다.

`Qt.lightGray`는 런타임에는 동작한다(PyQt5가 `Qt`에 열거형 멤버를 노출한다).
`Qt.GlobalColor.lightGray`와 값이 같은 것을 확인하고 후자로 바꿨다.

## `progress_dialog.py`: exclude에서 뺄 만했다

`ui/dialogs/progress_dialog.py`는 "Qt dialog with parent type issues"라는 사유로
통째로 exclude돼 있었다. 16건 중 12건이 한 뿌리에서 나왔고, 그 뿌리는 타입
문제이기 이전에 **실제 위험**이었다:

```python
self.parent = parent            # QWidget.parent() 메서드를 덮어씀
self.layout = QVBoxLayout(self) # QWidget.layout() 메서드를 덮어씀
```

`self.parent()`나 `self.layout()`을 호출하는 코드는 전부 깨진다. 사용처를 먼저
확인했더니 둘 다 이 파일 안에서만 쓰이고 있어서 — 외부에서 `dialog.parent`를
읽는 곳도, 테스트도 없었다 — `parent_widget` / `main_layout`으로 개명했다.
이유를 주석으로 붙여뒀다. exclude 사유가 "타입 이슈"였지만 실제로는 가려져
있던 결함이었던 셈이다.

나머지는 `deque`/`list`의 타입 주석 3건과, `m_app`에 대한 `union-attr` 3건.
후자는 `ui/main_window.py:48`에 이미 확립된 패턴(`CTHarvesterApp | None` 선언 +
사용 전 `if not self.m_app:` 가드)이 있어 그대로 가져왔다. `update_language()`가
`m_app`이 없을 때 조용히 죽는 대신 경고 로그를 남기고 반환한다.

## 정작 더 중요했던 발견: 세 곳이 다른 mypy를 돌리고 있었다

범위를 넓히면서 세 군데의 mypy 호출을 맞춰야 했는데, 비교해보니 애초에 서로
다른 검사를 하고 있었다.

| 곳 | 명령 | 환경 |
|---|---|---|
| CI (`test.yml`) | `mypy --config-file pyproject.toml core/ utils/` | dev 락 (mypy 1.20.2) |
| `make type-check` | `mypy . --ignore-missing-imports` | 개발자 환경 |
| pre-commit | mirrors-mypy, 파일 단위 | **격리 venv, mypy v1.8.0** |

pre-commit이 가장 나빴다. `rev: v1.8.0`은 락파일의 1.20.2와 두 해 가까이
벌어져 있었고, `additional_dependencies`로 선언한 `types-Pillow`와
`PyQt5-stubs`는 **어느 락파일에도 없다**. mypy의 답은 설치된 스텁에 따라
달라지므로, 이 훅과 CI는 양방향으로 어긋날 수 있었다 — 훅이 통과시킨 것을
CI가 잡거나, 그 반대거나.

이 리포는 ruff를 `pyproject.toml` / `.pre-commit-config.yaml` / CI 세 곳에
같은 버전으로 못박는 규율을 이미 지키고 있다. mypy만 예외였다. 버전 세 개를
쫓아다니는 대신 **훅이 프로젝트 자체 mypy로 CI와 같은 명령을 돌게** 했다:

```yaml
- repo: local
  hooks:
    - id: mypy
      entry: mypy --config-file pyproject.toml core/ utils/ ui/
      language: system
      pass_filenames: false
```

`pass_filenames: false`는 의도적이다. 파일 부분집합을 받은 mypy는 디렉토리를
받은 mypy와 import를 다르게 따라가므로, 같은 답을 보장하려면 CI 호출을 그대로
반복하는 수밖에 없다. `make type-check`도 같은 명령으로 통일했다. 이제 버전은
dev 락 한 곳에서만 관리된다.

`language: system`의 대가는 `make install-dev` 없이 pre-commit을 돌리면 훅이
"command not found"로 실패한다는 것이다. 조용한 불일치보다 시끄러운 실패가 낫다.

## 부수적으로: `docs/_build/` 24MB

작업 트리에 untracked로 24MB가 남아 있었다. 매뉴얼이 `docs/manual/`로 옮겨지기
전(devlog 107) 레이아웃의 잔재인데, `.gitignore`는 이동 후 경로인
`docs/manual/_build/`만 막고 있어서 옛 경로가 그대로 노출돼 있었다. 삭제하고
ignore 규칙을 경로가 아닌 **디렉토리 이름**(`_build/`)으로 바꿨다 — 다음에
빌드 위치가 또 옮겨져도 같은 일이 반복되지 않도록.

## 결과

- `mypy --config-file pyproject.toml core/ utils/ ui/` → **43개 파일, 이슈 없음**
- 전체 스위트 1,305 passed / 5 skipped, 회귀 없음
- 남은 것은 `ui/widgets/` 38건 (`mcube_widget.py` 27, `object_viewer_2d.py` 11).
  대부분 `Qt.LeftButton` 계열의 기계적 수정이고, 나머지는 `union-attr` 9건과
  `override` 3건. 같은 방식으로 파일 하나씩.

## 배운 것

**exclude 사유는 유통기한이 있다.** `progress_dialog.py`의 "Qt dialog with
parent type issues"는 사실이었지만, 그 "parent type issue"의 정체는 Qt 메서드를
덮어쓰는 속성이었다. 제외 목록에 넣고 나면 아무도 다시 재보지 않기 때문에,
사유가 여전히 유효한지는 재보기 전에는 알 수 없다. 실제로 재보니 `ui/` 전체가
6건이었다 — 넓히기를 미룰 이유가 처음부터 크지 않았다.

**같은 도구를 세 곳에서 돌린다면 세 곳이 같은 답을 내는지 확인해야 한다.**
게이팅으로 만드는 것과, 게이트가 로컬에서 보는 것과 같은 것을 보는 것은
별개의 일이다.
