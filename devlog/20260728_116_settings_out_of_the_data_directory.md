# 설정을 데이터 디렉토리 밖으로 (PaleoBytes 규약 R02)

2026-07-28

devlog 115에서 "사용자 데이터를 한 디렉토리로" 모으면서 설정 파일도 거기 넣었다.
PaperMeister에서 같은 문제를 검토한 결과 문서(`20260728_R02_Config_File_Location_Convention.md`)가
**그 결정을 뒤집는다.** 규약을 받아 적용했다.

---

## 🔀 무엇이 바뀌나

| | devlog 115 | R02 적용 후 |
|---|---|---|
| 설정 | `~/PaleoBytes/CTHarvester/preferences.json` | OS 설정 위치 아래 `PaleoBytes/CTHarvester/preferences.json` |
| 로그 | `~/PaleoBytes/CTHarvester/logs/` | 그대로 |

```
Windows   %LOCALAPPDATA%\PaleoBytes\CTHarvester\preferences.json
macOS     ~/Library/Application Support/PaleoBytes/CTHarvester/preferences.json
Linux     ~/.config/PaleoBytes/CTHarvester/preferences.json
```

## 🤔 115의 논거가 어디서 틀렸나

115에서 든 근거는 "프로필 백업이 디렉토리 하나 복사로 끝난다"였다. 이건 **설정도
백업 대상이라는 전제**를 깔고 있는데, R02는 바로 그 전제를 친다: 설정은 창 위치·
스레드 수 같은 **기기 종속 상태**이고, 잃으면 다시 지정하면 그만이다. 백업·동기화·
이전의 대상 여부가 데이터와 정반대다. 하나로 묶으면 편한 게 아니라, **성격이 다른
두 가지를 같은 정책으로 다루게 된다.**

더 결정적인 것은 부트스트랩 논거다. 데이터 위치를 설정 가능하게 만드는 순간
(`CTHARVESTER_DATA_DIR`은 이미 그렇다), 설정 파일이 데이터 디렉토리 안에 있으면
**데이터 위치를 알려고 설정을 읽어야 하고 설정을 읽으려고 데이터 위치를 알아야 한다.**
115의 배치는 이 순환을 아직 밟지 않았을 뿐 이미 만들어 두고 있었다.

**"하나로 모으는 것"이 목적이 아니라는 게 요지다.** 115가 고친 진짜 문제는 소유자가
네 명이라 서로 어긋난 것이지, 파일이 여러 디렉토리에 있는 것이 아니었다. 소유자는
여전히 `utils/paths.py` 하나이고, 루트만 둘이다.

## ⚙️ 구현에서 정한 것

- **`platformdirs`로 해석.** 직접 조립하면 `XDG_CONFIG_HOME` 폴백과 현지화된 Windows
  폴더명에서 깨진다. `QStandardPaths`도 정확하지만 **Qt를 끌어온다** —
  `utils/paths.py`는 CLI·스크립트가 import하는 모듈이라 헤드리스 환경에서 GUI 툴킷을
  요구하게 된다. 순수 파이썬이라 플랫폼별 wheel 문제도 없다(락 3종 모두 동일 버전).
- **벤더 세그먼트는 직접 붙인다.** `platformdirs`에 `appauthor`를 넘기면 **Windows에서만**
  반영된다. macOS·Linux 관례에 벤더 디렉토리가 없어 의도적으로 무시하기 때문이다.
  루트만 받아 `PaleoBytes/CTHarvester`를 join한다.
- **로그는 안 옮긴다.** 로깅은 설정을 읽기 전에 세팅되므로, 로그 위치를 설정에
  따르게 하면 초기 로그를 버리거나 이중 초기화를 해야 한다. 장애를 볼 때 로그가
  데이터 옆에 있는 편이 낫기도 하다.
- **마이그레이션은 넣지 않았다.** R02 체크리스트에는 있지만, 이 저장소는 사용자가
  없다는 것이 확인됐다(devlog 114에서 인스톨러 업그레이드 안내를 걷어낸 것과 같은
  판단). 필요해지면 첫 읽기에 거는 방식으로 붙이면 된다 — 진입점이 아니라 첫 읽기여야
  스크립트 경로도 함께 덮인다는 것이 R02의 지적이다.

## 🔍 검증

- `test_settings_are_not_stored_inside_the_data_directory` — **오버라이드를 모두 걷어내고**
  실제 `platformdirs`/홈 디렉토리 해석으로 두 경로를 구해 포함 관계가 없음을 확인한다.
  환경변수로 갈라 놓고 "다르다"고 주장하면 동어반복이라 그렇게 하지 않았다.
- `test_config_directory_carries_the_vendor_segment` — `appauthor`를 안 쓰고 직접
  붙였는지를 못 박는다. 이걸 놓치면 mac/Linux에서만 조용히 사라진다.
- `--self-test`로 실제 부팅: `<config>/preferences.json`과 `<data>/logs/CTHarvester.log`가
  각각 생기고 서로 섞이지 않는 것을 확인.
- 전체 스위트 1326 passed. 락파일 9종 재생성 후 `make lock-check` 통과.

## 🧹 문서와 번역

매뉴얼에서 경로를 바꾸는 것으로 끝나지 않았다 — **"모든 것이 한 디렉토리에 있어
백업이 복사 하나"라는 문장 자체가 이제 틀리므로** 그 근거 문단을 다시 썼고, 환경변수
설명도 `CTHARVESTER_CONFIG_DIR`/`CTHARVESTER_DATA_DIR` 둘로 나눴다. `Linux/macOS`로
묶여 있던 표기는 갈라야 했다 — 이제 경로가 실제로 다르다.

한국어 카탈로그는 같은 세션에서 막 100%로 채운 참이라, 소스가 바뀐 만큼 다시
동기화하고 fuzzy를 정리했다. 이번에는 **인덱스가 아니라 msgid로 적용**했다. 직전
커밋에서 인덱스 기준 적용이 소스 변경으로 한 칸씩 밀리는 사고를 냈기 때문이다.
적용 스크립트에 "fuzzy가 하나도 남지 않아야 한다"는 단언을 넣었다 — fuzzy 항목은
컴파일 때 버려지므로, **번역을 입은 미번역 문자열**이 된다.

## 💡 교훈

1. **"한곳에 모으기"는 그 자체로 미덕이 아니다.** 무엇을 모으는지가 먼저다. 성격이
   다른 두 가지를 모으면 정책이 하나로 붙어 버린다.
2. **설정 가능한 위치 안에 설정을 두지 마라.** 지금 순환이 없어도, 그 기능을 켜는
   순간 생긴다. 분리는 기능의 선행 조건이다.
3. **같은 세션 안에서도 결정은 뒤집힌다.** 115를 쓸 때의 근거는 그 시점에 알던 것
   기준으로는 타당했다. 기록을 남기는 값어치는 뒤집혔을 때 *왜* 뒤집혔는지가 남는
   데 있다.
4. **자동 적용 도구는 실패를 단언으로 잡아야 한다.** 인덱스 밀림은 조용히 지나갔고,
   msgid 기준 + fuzzy 0 단언은 시끄럽게 실패한다.
