# 123 — mypy 2: 하한을 올리고, strict_bytes가 잡은 한 줄을 고침

2026-11-11. devlog 122에서 보류한 mypy 2를 진행. Dependabot #8(`<3.0.0`)을 대체.

## 순서

devlog 110의 원칙대로다. 상한을 넓히는 것은 허락일 뿐이고, 하한을 올려야 실제로
움직인다. #8은 상한만 넓혀 락이 1.20.2에 그대로 머물므로 그 자체로는 효과가 없다.
그래서 두 커밋으로 나눴다.

1. **mypy 1.20.2에서 고친다.** `[tool.mypy]`에 `strict_bytes = true`를 명시해 1.x에서
   2.x의 기본값을 재현하고, 그 상태에서 오류를 없앤다. 1.x와 2.x의 판정이 같아지므로
   버전을 올리는 커밋에는 타입 변화가 섞이지 않는다.
2. **하한을 `>=2.0.0,<3.0.0`으로 올리고** `make lock`.

## 고친 한 줄

`ui/widgets/object_viewer_2d.py`의 `apply_threshold_and_colorize`에서 문제가 된 줄:

```python
qt_image = QImage(rgb_array.data, ...)          # memoryview → strict_bytes에서 오류
modified_pixmap = QPixmap.fromImage(qt_image.copy())
```

이렇게 바꿨다.

```python
rgb_bytes = rgb_array.tobytes()
qt_image = QImage(rgb_bytes, ...)
return QPixmap.fromImage(qt_image)
```

`.tobytes()`에서 복사가 한 번 늘고 `.copy()`가 빠지므로 복사 횟수는 그대로다.
`.copy()`를 빼도 되는지는 직접 쟀다(PyQt 5.15.11 / Qt 5.15.14, offscreen).

- `QImage(bytes, ...)`는 버퍼를 **복사하지 않는다.** `constBits()` 주소가 bytes의
  데이터 주소와 같다.
- PyQt는 QImage가 그 bytes를 **참조로 붙잡게** 한다. 생성 전후 `sys.getrefcount`가
  2에서 3이 된다. 따라서 QImage가 살아 있는 동안 버퍼가 먼저 해제되는 일은 없다.
- `QPixmap.fromImage()`는 RGB888을 픽스맵의 자체 저장소(`Format_RGB32`)로
  **변환·복사한다.** 픽스맵 쪽 주소는 bytes와 다르고, bytes와 QImage를 지운 뒤
  `gc.collect()`를 하고 해제된 메모리를 다른 할당으로 덮어써도 픽셀이 그대로다.

## 테스트

이 함수에는 직접 테스트가 없었다. `tests/ui/test_object_viewer_2d.py`에 3개를 추가했다.

- crop 박스 안에서 임계값을 넘는 픽셀만 초록으로 칠해지는지(일반, `is_inverse` 둘 다).
  박스 끝 포함(`y2 + 1`)도 함께 고정된다.
- 반환된 픽스맵이 임시 버퍼가 해제·재사용된 뒤에도 같은 픽셀을 갖는지.

이 테스트들은 **고치기 전 코드에서도 통과하는 것을 먼저 확인했다.** 동작을 바꾸지
않았다는 근거로 쓰기 위해서다.

테스트를 쓰다가 생긴 두 가지 문제:

- `monkeypatch.setattr(viewer, ...)`는 teardown에서 이미 삭제된 위젯에 속성을
  되돌리려다 `RuntimeError`를 냈다. 인스턴스 속성으로 직접 대입하는 것으로 바꿨다.
- 부모 위젯을 fixture 안의 지역 변수로 두면, pytest-qt가 위젯을 **약한 참조로만**
  붙잡으므로 테스트의 `gc.collect()`가 부모를 수거하면서 뷰어까지 함께 지운다.
  기존 테스트처럼 별도 fixture로 두어 살려 둔다.

## 관찰 (고치지 않음)

**이 함수는 컬러 입력에서 R과 B를 바꾼다.** `qt_pixmap.toImage()`는 `Format_RGB32`를
돌려주는데, 리틀 엔디언에서 메모리상 순서는 **B, G, R, A**다. 그런데 앞 세 바이트를
RGB로 읽어 RGB888 QImage를 만들고, 임계값 비교도 채널 0(실제로는 B)으로 한다. CT
슬라이스는 회색(R = G = B)이라 결과가 같아서 드러나지 않았다. 처음에 무작위 컬러
입력으로 테스트를 썼을 때 픽셀 66.8%가 어긋나서 알게 됐다. 이 PR의 범위가 아니므로
테스트를 회색 입력으로 바꾸고 fixture 주석에 그 이유를 적었다. 컬러 입력을 받게
되는 날 다시 볼 것.

## 검증 (Linux, Python 3.12, offscreen)

- mypy 1.20.2 + `strict_bytes = true`: 수정 전 오류 1건, 수정 후 통과.
- mypy 2.4.1(새 dev 락으로 `--require-hashes` 설치): 통과.
- `make lock`: dev 락 3개만 바뀜. `mypy` 1.20.2 → 2.4.1, `librt` 0.13.0 → 0.16.0,
  `ast-serialize` 0.13.1 신규. 둘 다 `# via mypy`다. `make lock-check` 통과.
- CI 선택(`-m "not slow and not benchmark" -n auto --timeout=60`): 1323 passed,
  3 skipped(121의 1320 + 새 테스트 3).
- ruff 0.17.1 check / format --check 통과.
