# 122 — ruff 0.17.1, 그리고 mypy 2를 미룬 이유

2026-11-11. Dependabot PR 두 건(#19 ruff, #8 mypy)을 현재 `main` 기준으로 다시 판단.
ruff는 이 브랜치로 대신 올리고, mypy는 보류.

## ruff 0.16.0 → 0.17.1 (#19 대체)

#19는 그대로 머지할 수 없었다.

- **CI가 돌지 않았다.** 머리 커밋이 `dependabot-lock-refresh.yml`이 `GITHUB_TOKEN`으로
  밀어 넣은 락 갱신 커밋이라, GitHub의 루프 방지로 체크가 하나도 붙지 않았다
  (GitGuardian만 있음). devlog 109에서 `LOCK_REFRESH_TOKEN` 없이 예상했던 그대로다.
- **`.pre-commit-config.yaml`의 `rev`를 올리지 않았다.** ruff는 `pyproject.toml`,
  `requirements-dev.txt`, pre-commit 세 곳에 같은 버전으로 고정하도록 주석에
  적혀 있다(포맷터 버전이 다르면 관계없는 PR이 빨개진다). Dependabot은 pip
  생태계만 보므로 pre-commit 쪽을 모른다.

그래서 `main`에서 새 브랜치를 따서 세 곳을 함께 올리고 `make lock`을 돌렸다.
락 9개 중 dev 락 3개에서 **ruff 한 줄만** 바뀌었다. 0.17.4가 나와 있지만 승인받은
범위인 0.17.1에 맞췄다.

검증(Linux, Python 3.12): `ruff check .` 통과, `ruff format --check .` 147개 파일
변경 없음, `make lock-check` 통과.

## mypy `<2.0.0` → `<3.0.0` (#8, 보류)

devlog 110에 따르면 상한만 넓히는 PR은 아무것도 바꾸지 않는다. 락이 1.20.2를
계속 고르기 때문이다. 그래서 실제로 2.x로 올렸을 때 어떻게 되는지 직접 재 봤다.
mypy 2.4.1과 2.0.0 모두, `core/ utils/ ui/`에서 **오류 1건**이 나왔다.

```
ui/widgets/object_viewer_2d.py:702: error: No overload variant of "QImage" matches
argument types "memoryview[int]", "Any", "Any", "Any", "Any"  [call-overload]
```

**원인: mypy 2.0이 `--strict-bytes`를 기본으로 켰다.** 이전에는 `memoryview`·
`bytearray`가 `bytes` 자리에 암묵적으로 통과했다. 확인:

- mypy 2.4.1 + `--no-strict-bytes` → 통과.
- mypy 1.20.2 + `--strict-bytes` → 같은 오류 1건.

즉 새 버전의 회귀가 아니라 규칙이 엄격해진 것이고, 걸리는 곳은
`QImage(rgb_array.data, ...)` 한 줄이다(`ndarray.data`는 `memoryview`). 런타임
동작은 문제가 없다. PyQt5가 버퍼 프로토콜로 받는다.

고칠 범위는 이 한 줄이다. 후보는 다음과 같다.

1. `QImage(rgb_array.tobytes(), ...)`. 타입이 맞는다. 복사가 한 번 늘지만 바로 아래에서
   어차피 `qt_image.copy()`를 하므로, 이 경우 그 `.copy()`를 빼면 복사 횟수는 같다.
   (`tobytes()`로 만든 `bytes`의 수명을 QImage가 붙잡지 않는다는 점은 확인 필요.)
2. `# type: ignore[call-overload]`에 근거를 적는 방법.
3. `[tool.mypy]`에 `strict_bytes = false`. 비권장이다. 규칙 전체를 끄게 된다.

1을 택하면 mypy 1.20.2에서 먼저 `strict_bytes = true`를 켜 고친 뒤, 하한을
`>=2.0.0`으로 올리는 PR(devlog 110의 "floor is force")로 가는 것이 순서다. #8 자체는
상한만 넓혀 효과가 없으므로 그 PR이 대체한다.
