# 124 — 임계값 오버레이가 컬러 입력의 R과 B를 바꾸던 문제

2026-11-11. devlog 123에서 관찰만 하고 남겨 둔 것을 고침. 사용자 요청("혹시 모르니
색깔 잘 맞춰줘").

## 무엇이 틀렸나

`ObjectViewer2D.apply_threshold_and_colorize`는 화면에 그릴 슬라이스 픽스맵을
`toImage()`로 꺼내 바이트를 직접 읽는다. 이 코드는 두 가지를 가정하고 있었다.

1. 바이트 순서가 R, G, B, A다.
2. 픽셀당 4바이트이고 행 끝에 패딩이 없다(`reshape((h, w, 4))`).

`toImage()`가 돌려주는 형식은 보통 `Format_RGB32`이고, 이것은 `0xffRRGGBB`라는
**32비트 정수**다. 그래서 리틀 엔디언(x86, ARM 모두)에서 메모리상 순서는
**B, G, R, A**다. 결과적으로 1이 틀렸다. 이 바이트를 RGB로 읽어 RGB888 QImage를
만드니 **출력에서 R과 B가 바뀌었다.** 또 임계값 비교는 채널 0을 쓰는데, 그것이
실제로는 B였다.

CT 슬라이스는 회색(R = G = B)이라 바뀌어도 같은 값이므로 아무도 볼 수 없었다.
드러난 것은 devlog 123에서 처음 무작위 컬러 입력으로 테스트를 썼을 때였다(픽셀
66.8% 불일치).

2는 운 좋게 맞고 있었다. Linux offscreen에서 8비트 PNG/TIFF/BMP, 16비트 TIFF/PNG,
RGB PNG를 `QPixmap(path)`로 읽어도, `scaled()`를 거쳐도, `toImage()`는 모두
`Format_RGB32`였다. 다만 투명도가 있는 이미지라면 `ARGB32_Premultiplied`(값이
알파로 곱해짐)가 올 수 있고, 다른 플랫폼에서는 확인하지 않았다.

## 변경

```python
qt_image = qt_pixmap.toImage().convertToFormat(QImage.Format_RGBA8888)
```

`toImage()`의 형식을 믿지 않고 명시적으로 변환한다. `Format_RGBA8888`은 엔디언과
무관하게 **바이트 순서 자체가** R, G, B, A이고, premultiplied가 아니며, 언제나
픽셀당 4바이트라 행 패딩이 없다. 두 가정이 모두 형식의 정의로 보장된다. 대가는
변환 복사 한 번이다(슬라이스 하나를 그릴 때마다).

임계값은 이제 실제로 **R 채널**에 대해 비교된다. 회색 입력에서는 이전과 같다.
컬러 입력에서 휘도(luminance)로 비교해야 하는지는 정하지 않았다. 컬러 CT를 받게
되면 그때 정할 일이다.

## 검증

- 테스트 입력을 회색에서 **R, G, B가 독립인 무작위 컬러**로 바꿨다(회색 입력이 바로
  이 결함을 가렸다). 칠해지지 않는 픽셀이 입력 그대로 나오는지 보는 테스트도 하나
  추가했다.
- **수정 전 코드에서는 4개 모두 실패**(픽셀 64.9~66.8% 불일치), 수정 후 통과.
- **회색 CT 입력에서는 출력이 바이트 단위로 동일함**을 확인했다. 8비트 PNG/TIFF/BMP와
  16비트 TIFF를 수정 전후 코드로 각각 돌려 sha256을 비교했다. 지금 쓰는 사용자의
  화면은 바뀌지 않는다.
- 픽셀 바이트를 Qt에서 직접 읽는 곳은 저장소 전체에서 이 함수 하나뿐이다
  (`constBits`/`bits()`/`frombuffer` 검색).
