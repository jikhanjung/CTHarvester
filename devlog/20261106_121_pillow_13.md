# 121 — Pillow 13: 상한이 수정 버전을 막고 있었다

2026-11-06. 의존성 범위 변경 + 락 재생성. 코드 변경 없음.

## 무엇이 문제였나

`Security` 워크플로가 2026-10-26, 11-02 두 번의 정기 실행에서 `main`을 빨갛게
만들었다. `pip-audit`이 **Pillow 12.3.0에서 39건**(PYSEC-2026-4326~4343,
CVE-2026-112xxx 묶음, CVE-2026-96638/96640/96778, GHSA-78g4-xqwv-q3g8)을 보고했고,
수정 버전은 전부 13.0.0이었다.

락만 다시 만들어서는 고쳐지지 않는 상태였다. 선언 범위가
`pillow>=12.3.0,<13.0.0`이라 **상한이 수정 버전을 정확히 배제**하고 있었다.
**devlog 101과 같은 일이 두 번째다.** 그때는 `<12.0.0` 상한이 11.3.0의 CVE 18건
수정을 막았고, 하한을 12.3.0으로 올리면서 상한을 `<13.0.0`으로 한 칸 옮겼다.
이번에는 그 `<13`이 같은 방식으로 막았다. 메이저 상한은 호환성을 지켜 주지만,
보안 수정이 새 메이저에만 나오면 **실패하는 것은 정기 pip-audit뿐**이고 그것도
상한을 직접 풀기 전까지는 계속 빨갛다. 이번에는 pillow에 대한 Dependabot PR도
열려 있지 않았고, 있었더라도 상한만 넓히는 PR은 락이 기존 핀을 선호해 효과가
없다(devlog 110).

같은 날 Modan2도 같은 39건으로 pip-audit이 실패하고 있었다(Modan2 #91). 거기서는
pillow에 범위가 없어 락이 12.3.0을 계속 고르던 경우였고, 원인은 다르지만 결과는
같았다.

## 변경

- `pyproject.toml`, `requirements.txt`: `pillow>=13.0.0,<14.0.0`. 하한을 13.0.0으로
  올려 취약 범위를 다시 들이지 않게 하고(devlog 109의 #5 사례), 상한은 한 메이저 위로.
- `make lock`: 락 9개 모두 **pillow 12.3.0 → 13.0.0 한 줄만** 바뀜. 다른 핀은 그대로.
- `CHANGELOG.md` `[Unreleased]`에 Security 항목.

## 검증 (Linux, Python 3.12, offscreen)

- `make lock-check`: 통과.
- `pip-audit -r requirements-{linux,windows,macos}.lock --no-deps`: 세 플랫폼 모두
  취약점 없음.
- CI와 같은 선택(`-m "not slow and not benchmark" -n auto --timeout=60`):
  **1320 passed, 3 skipped**. `pyproject.toml`의 `filterwarnings = ["error", ...]`가
  그대로 적용된 실행이므로 Pillow 13의 DeprecationWarning도 없다.
- smoke(`tests/test_smoke.py -m smoke`): 66 passed.
- `slow` 중 benchmark가 아닌 것: 13 passed, 2 failed — **둘 다 Pillow와 무관**:
  - `test_large_dataset_performance`는 이 기기에서 4분 반이 걸려 임의로 준
    `--timeout=240`을 넘겼다. 타임아웃 없이 재면 **12.3.0 282s / 13.0.0 266s**로
    둘 다 통과, 13이 오히려 약간 빠르다.
  - `test_continuous_processing`의 `PytestUnraisableExceptionWarning`(닫히지 않은
    `FileIO`)은 바로 앞 테스트가 타임아웃으로 중단되며 남긴 파일 객체가 다음 테스트
    도중 수거된 것으로 보인다. 단독 실행은 12.3.0, 13.0.0 모두 2회씩 통과.

## 관찰

- 이 benchmark 테스트들은 기본 `/tmp`(tmpfs, 사용자 쿼터)에서 돌리면
  `Disk quota exceeded`로 실패한다. 디스크 위의 `--basetemp`가 필요하다.
- 처음에 `-W error::DeprecationWarning`을 명령행에 덧붙였더니 스위트가 20분
  타임아웃 안에 끝나지 않았다(같은 선택이 플래그 없이 28초). 명령행 `-W`가
  `filterwarnings`의 예외 목록(`sipPyTypeDict` 등)을 덮었기 때문으로 보이나
  확인하지는 않았다. 어쨌든 이 프로젝트는 이미 모든 경고를 오류로 다루므로
  덧붙일 필요가 없다.
